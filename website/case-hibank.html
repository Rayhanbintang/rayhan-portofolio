297 manifests, rebuilt from live state instead of lifted

Moving a production Kubernetes estate from GKE to Amazon EKS is only a migration in the marketing sense. The workload definitions are full of platform-specific assumptions that have no equivalent on the other side. This is how I rebuilt them, why I wrote a toolchain instead of editing YAML by hand, and what the cutover gate caught.

Context and constraints

A core banking and Buy Now Pay Later platform running on Google Kubernetes Engine, moving to Amazon EKS. Regulated financial services, so the cutover window was short and the appetite for discovering problems in production was zero.

The workload layer could not simply be copied. GKE-specific constructs were everywhere: SecretProviderClass resources reading from GCP Secret Manager, Filestore-backed volumes, GKE Ingress with BackendConfig, NodePort services fronted by Google load balancers, image references pointing at Artifact Registry, and service discovery resolving through names that would not exist on the other side.

Why a toolchain and not an afternoon of find-and-replace

297 manifests across 11 resource kinds: 83 SecretProviderClasses, 64 Services, 64 ConfigMaps, 61 Deployments, 7 ServiceAccounts, 6 Ingresses, 4 PersistentVolumes, 3 StatefulSets, 2 StorageClasses, 2 PersistentVolumeClaims and a BackendConfig. Hand-editing that once is tedious. The problem is that you do not do it once. You do it for staging, then again for UAT, then again for production, and each time the source cluster has moved on.

So I wrote 46 scripts in Python and Bash, structured as a pipeline rather than a pile of one-offs:

  • Extract live state from the source cluster, because what is running is the only definition that is actually true
  • Sanitize away runtime fields, last-applied-configuration annotations and cluster-scoped metadata that would not transplant
  • Convert each GKE construct to its AWS equivalent
  • Verify the result against the source before anyone touched DNS

Running the whole thing per environment took minutes and produced the same answer every time. That repeatability is the entire value: it turned "we migrated staging, now do it again from memory" into a command.

The conversions

  • SecretProviderClass reading GCP Secret Manager → native Kubernetes Secrets
  • Filestore volumes → EFS CSI StorageClass, PersistentVolume and Claim
  • GKE Ingress and BackendConfig → nginx-ingress with per-environment Helm values
  • NodePort behind a Google load balancer → ClusterIP behind NLB annotations
  • Artifact Registry image references → Amazon ECR, across a 65-image inventory, digest-pinned
  • Service-discovery DNS rewritten, and log shipping sidecars re-pointed at the AWS-side collector

Decisions and trade-offs

decision 01 · source of truth

Rebuild from the live cluster, not from the repository. The manifests in version control had drifted from what was actually running, which is normal and is exactly why lift-and-shift migrations fail in week three. Extracting live state meant inheriting some things nobody remembered configuring, and it meant a sanitization step that would not have been necessary otherwise. It also meant the target ran what production ran, rather than what production was believed to run.

decision 02 · gate the cutover

Verification scripts before DNS, not after. The estate referenced dependencies by IP in more places than anyone expected: a 92-row inventory of source-side addresses that had to be re-mapped onto DNS names, plus a 40-row configuration mapping. I wrote checks that compared the mapping and confirmed cluster readiness, and made passing them a precondition for the switch. They caught mismatches while rolling back was still free. The cost is a slower cutover checklist; the alternative is finding out from a customer.

decision 03 · secrets

Native Secrets rather than reproducing the CSI driver pattern. Eighty-three SecretProviderClass resources could have been rebuilt against AWS Secrets Manager through the CSI driver, preserving the shape of the original. I converted them to native Kubernetes Secrets instead, because carrying an extra moving part across a migration boundary adds a failure mode precisely when you have the least capacity to debug one. The trade-off is a secret-rotation story that is now the platform's problem rather than the driver's, and that was the right thing to take on deliberately rather than inherit by accident.

The cluster underneath

Six environments got the same bootstrap: BNPL staging, UAT and production, plus digital production, ITSM production and an infrastructure management environment. Each one received VPC CNI custom networking with a per-AZ ENIConfig keyed on the zone label, prefix delegation for pod density, pod security groups where a workload needed its own network identity, nginx-ingress installed through Helm with per-environment values behind an NLB, and the AWS Load Balancer Controller.

Around the migration itself sat the platform baseline: a Terraform landing zone with CloudTrail, AWS Config, KMS, SSM patching and central backup; AWS SSO rolled out across 25 accounts and 109 assignments; a Cloud Run job re-platformed onto container-image Lambda; and log analysis moved onto S3 and Athena so retention stopped being billed at hot-storage rates.

What I would do differently

The toolchain was written as the migration progressed, which meant early scripts had to be revisited once the later pattern became clear. Spending the first two days designing the pipeline stages before writing any of them would have produced a cleaner set with less overlap.

The harder lesson is about what happens after. I handed over infrastructure defined in Terraform. It is now managed without it. That is the customer's call to make and the engagement was scoped as a delivery, but it is the reason I have come to care more about whether a platform is adopted than whether it is correct. Code that describes an estate nobody updates through it is an artifact, not infrastructure. Building the handover to include the operating model, not just the modules, is the thing I would insist on earlier.
