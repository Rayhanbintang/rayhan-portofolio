A greenfield AWS platform, and the 59 pipelines that had to run on it

A regional Indonesian bank needed its mobile banking estate stood up on AWS from nothing: network, clusters, registry, delivery, and enough developer experience that application teams could ship without learning Terraform first. This is what the platform ended up being, and the three decisions I would defend in a review.

Context and constraints

Nothing existed at the start. No landing zone, no network, no registry, no pipelines. The application estate was already written and already had opinions, which meant the platform had to accommodate the applications rather than the other way around.

Three constraints shaped everything. It is a bank, so the network design had to survive an audit and the access path to anything private had to be justifiable. The timeline was compressed. And the application teams were not infrastructure teams, so any solution that required each of 64 repositories to author its own CI would have quietly failed at repository forty.

What I built

Terraform, in five stacks

Networking, cluster, registry, delivery and workload each own a stack with its own state, driven by for_each so the three clusters are the same code with different inputs rather than three copies that drift apart by month two. Three Amazon EKS clusters on 20 managed nodes, with the ALB controller, metrics-server and cluster autoscaler installed via Helm.

IP space was the interesting part. Pod density on the intended instance sizes did not fit the addresses available in the primary CIDR, so pods run on a secondary CIDR through VPC CNI custom networking, with a per-AZ ENIConfig keyed on the zone label, prefix delegation for density, and pod security groups where a workload needed its own network identity. IRSA everywhere, so nothing carries a node role it should not have.

Delivery: 64 repositories, three templates

64 application repositories onto GitLab CI, building into Amazon ECR, delivered onto the clusters through a hub-and-spoke ArgoCD. At handover, 63 services were running healthy across the three clusters, every deployable service in the estate.

The part I care about most is not the count. Rather than write 64 pipelines, I built three shared templates with an opt-in image-bump-and-sync loop: the pipeline builds, tags, pushes, updates the manifest and lets ArgoCD converge. A team enables the whole delivery path by setting a single variable. That carried 59 repositories with every pipeline green, and it means the next change to how deployment works is one commit in one place instead of a migration.

Decisions and trade-offs

decision 01 · autoscaling

KEDA on connection count, because CPU was lying. One service holds long-lived WebSocket connections. Its pods sit at a steady, unremarkable CPU utilization whether they are holding fifty connections or five thousand, so a CPU-based HPA would have scaled late on the way up and not at all on the way down. I moved it to KEDA scaling on connection count. The trade-off is a second scaling mechanism to understand and an external metric source to keep healthy, which is a real cost. It was worth it here because the alternative was an autoscaler that could not observe the thing it was supposed to react to.

decision 02 · developer experience

Opt-in templates rather than mandated ones. Shared CI can be imposed, and then every team with an unusual build fights it and forks it. Making adoption a single variable meant teams that fit the pattern got it for free and teams that did not could stay out without blocking anyone. The cost is that the templates have to stay genuinely good, because nothing forces their use. 59 of 64 chose them.

decision 03 · owning the drift

Reconcile the console back into state, do not import and move on. During a compressed build, things get clicked. I worked the drift back into Terraform until plan reported no changes, rather than leaving a codebase that describes an estate nobody actually has. Slower in the moment. The alternative is handing over infrastructure-as-code that is neither.

Where the platform ended and I kept going

Several services were reported as blocked by on-premise network connectivity. They were not. Every one of them turned out to be a source or configuration defect: services pointing at the wrong dependency, Java applications failing during boot for reasons that surfaced as connection errors much later in the stack.

Fixing them meant working inside the application layer, repointing dependencies through settings.xml and Dockerfile build variables, and reading enough of the boot sequence to tell a genuine network reachability problem from an application that never got far enough to open a socket. That is not platform work, strictly. But "the network is blocked" is the most expensive wrong diagnosis available on a migration, and someone has to be willing to open the application to disprove it.

Numbers

  • 3 EKS clusters, 20 managed nodes, from a five-stack Terraform layout using for_each
  • 64 repositories onboarded to GitLab CI and Amazon ECR
  • 63 services healthy under hub-and-spoke ArgoCD, every deployable service in the estate
  • 59 repositories on the three shared pipeline templates, all pipelines green
  • 99.7% success rate under a 25,000-user load, alongside AZ-failure resilience testing
  • An x86 versus Graviton benchmark to inform node group sizing
  • terraform plan reporting no changes at handover

What I would do differently

The shared templates arrived after the first wave of repositories was already onboarded, which meant retrofitting teams that had started writing their own CI. Building the template layer first, even in rough form, would have saved that rework. The lesson generalizes: on a platform build, the developer-facing interface is not the thing you add once the infrastructure is stable. It is the thing that determines whether the infrastructure gets used the way you designed it.

I would also have pushed harder, earlier, for read access to application source. The week spent proving that "the network is blocked" was actually four application defects was a week that a single afternoon of code reading at the start would have compressed considerably.
